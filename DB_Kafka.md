## Чем SQL отличается от NoSQL - подходы

- Ответ

    SQL и NoSQL - это две разные категории систем управления базами данных, отличающиеся по подходам к хранению, обработке и организации данных.

    Основные подходы:
    1. SQL (реляционные базы данных) используют таблицы с четко заданной схемой и отношениями между данными. Данные строго структурированы, и операции выполняются с помощью языка SQL (Structured Query Language). Поддерживают транзакции с гарантией ACID - целостности, изоляции и надежности.

    2. NoSQL (нереляционные базы данных) применяют гибкие модели хранения данных: документы (JSON), ключ-значение, графы, колонки и другие. Это упрощает масштабирование и работу с разнородными или быстро меняющимися данными, часто с применением модели BASE - высокой доступности и «конечной согласованности».

- ACID / BASE

    ACID - это набор свойств, обеспечивающих надежность транзакций в реляционных базах данных:
    1. Atomicity (Атомарность): Транзакция либо выполняется полностью, либо не выполняется вовсе.
    2. Consistency (Согласованность): После выполнения транзакции база остается в корректном состоянии.
    3. Isolation (Изоляция): Параллельно выполняющиеся транзакции не влияют друг на друга.
    4. Durability (Долговечность): Результаты успешной транзакции сохраняются в базе даже при сбоях.

    Пример применения ACID: банковские системы, где крайне важна целостность и согласованность данных при переводах денег, чтобы исключить ошибки и потери.​

    BASE - это модель, обычно применяемая в распределенных и NoSQL базах, ориентированная на высокую доступность и масштабируемость, где строгая согласованность не всегда возможна:
    1. Basically Available (Базовая доступность): Система гарантирует доступность данных с некоторыми ограничениями.
    2. Soft state (Мягкое состояние): Состояние базы может изменяться со временем без фиксированной согласованности в каждый момент.
    3. Eventual consistency (Конечная согласованность): Данные синхронизируются и приходят к согласованному состоянию со временем.

    Пример применения BASE: крупномасштабные веб-приложения и распределенные системы, такие как социальные сети или распределенные кэши, где важна высокая скорость и отказоустойчивость, и временные расхождения в данных допустимы.

## Что такое CAP-теорема? Какие trade-offs между консистентностью, доступностью и устойчивостью вы видели на практике?

- Ответ
    CAP-теорема - формулирующая три ключевых свойства системы: Consistency (Согласованность), Availability (Доступность) и Partition Tolerance (Устойчивость к разделению сети). Теорема утверждает, что в любой распределённой системе одновременно можно полностью обеспечить только два из трёх свойств, поскольку сетевые разделения (partition) в распределённых системах неизбежны.

    1. Согласованность (Consistency): Все узлы системы видят одинаковые данные в один и тот же момент времени. После записи данные сразу доступны всем.

    2. Доступность (Availability): Каждый запрос к системе получает успешный ответ, даже если некоторые узлы недоступны.

    3. Устойчивость к разделению (Partition Tolerance): Система продолжает работать, несмотря на потери связи между узлами.

    Trade-offs в практике:
    1. CP-системы (Consistency + Partition tolerance): Жертвуют доступностью при разделении сети, могут возвращать ошибки или ждать восстановления связи, чтобы сохранять целостность данных. Пример: HBase, MongoDB в некоторых режимах.

    2. AP-системы (Availability + Partition tolerance): Гарантируют доступность и устойчивость, но допускают временную рассогласованность данных (eventual consistency). Пример: Cassandra, Amazon DynamoDB.

    3. CA-системы (Consistency + Availability): Возможны только при отсутствии разделений сети, подходят для локальных систем с высокой согласованностью и доступностью, но без устойчивости к разделению. Пример: PostgreSQL, MySQL

## Какие виды индексов знаете и как их использовать для ускорения запросов?

- Ответ

    Индексы в базе данных - это специальные структуры, которые ускоряют выполнение запросов, позволяя быстро находить нужные данные без полного перебора таблицы.

    Основные виды индексов и их использование:
    1. Кластеризованный индекс (Clustered Index): Определяет физический порядок строк в таблице. Каждая таблица может иметь только один кластеризованный индекс. Хорош для частого сортирования или диапазонных запросов по ключу.
    2. Некластеризованный индекс (Non-clustered Index): Не меняет физический порядок данных, а создает отдельную структуру с указателями на строки таблицы. Можно создавать несколько таких индексов для ускорения различных запросов.
    3. Уникальный индекс (Unique Index): Гарантирует уникальность значений в столбце или наборе столбцов, предотвращая дублирование. Часто используется для первичных ключей.
    4. Составной (Composite) индекс: Индекс на нескольких колонках одновременно, полезен, когда запросы используют комбинацию этих полей.
    5. Хеш-индекс (Hash Index): Хорош для поиска по точному совпадению (операции равенства). Часто применяется в NoSQL и некоторых СУБД для оптимизации скорости.
    6. B-Tree индекс: Самый распространённый индекс в реляционных СУБД. Реализован в форме сбалансированного дерева, подходит для операций сравнения и сортировки.
    7. Покрывающий индекс (Covering Index): Включает все столбцы, требуемые для запроса, позволяя не обращаться к основной таблице.
    8. Функциональный индекс (Functional Index): Индекс, построенный на результате функции от столбца (например, UPPER для строк), ускоряет запросы с выражениями.
    9. Частичный индекс (Partial Index): Индекс на часть таблицы, с условиями фильтрации, уменьшающий размер индекса.

    Применение для ускорения запросов:
    1. Индексы ускоряют поиск по ключам и условиям WHERE.
    2. Составные индексы оптимизируют запросы с несколькими фильтрами
    3. Покрывающие индексы уменьшают количество обращений к таблице.
    4. Хеш-индексы подходят для операций равенства, B-Tree - для диапазонных запросов и сортировки.
    5. Важно не злоупотреблять индексами, так как они замедляют операции вставки и обновления

- Ускорение работы баз данных

    Поиск медленных запросов:
    1. Включение логирования медленных запросов через параметры log_min_duration_statement, где указывают порог времени, после которого запрос считается медленным и логируется.
    2. Использование системных представлений и расширений, например, pg_stat_statements, для сбора статистики по выполнению запросов - частота, среднее время, количество вызовов.
    3. Мониторинг через инструменты визуализации и метрик (Prometheus + Grafana, pgAdmin).

    Анализ запросов:
    1. Использование команды EXPLAIN (ANALYZE, BUFFERS) для подробного анализа плана выполнения конкретного запроса. В плане видно использование индексов, время выполнения операций, количество строк.
    2. Оценка проблем с последовательным сканированием (Seq Scan), неправильным выбором индексов, перекрестными соединениями и узкими местами.
    
    Оптимизация запросов:
    1. Создание или корректировка индексов по колонкам, участвующим в фильтрах и соединениях.
    2. Переписывание запросов для уменьшения объема обрабатываемых данных, например, используя подзапросы, оконные функции, агрегации.
    3. Настройка параметров конфигурации PostgreSQL, таких как work_mem, effective_cache_size и random_page_cost.
    4. Удаление ненужных или неиспользуемых индексов, так как они замедляют операции записи.
    5. Использование материализованных видов для часто запрашиваемых агрегатов.
    6. Введение партиционирования таблиц при работе с большими объемами данных

## Репликация и шардинг: сравните подходы, поясните их особенности и способы применения

- Ответ

    Репликация и шардинг - это два разных подхода к масштабированию баз данных, которые решают разные задачи и имеют свои особенности.

    Репликация:
    1. Это копирование данных с одного основного (primary/master) сервера на один или несколько вторичных (replica/slave) серверов.
    2. Основная цель - повышение отказоустойчивости, доступности и масштабируемости чтения, так как чтение может обрабатываться с реплик.
    3. Репликация бывает синхронной (где записи подтверждаются всеми репликами) и асинхронной (записи подтверждаются основным, реплики обновляются с задержкой).
    4. Применяется для обеспечения резервного копирования, балансировки нагрузки на чтение и миграции без простоя.

    Шардинг:
    1. Деление базы данных на части (шарды), каждая из которых хранится на отдельном сервере или кластере.
    2. Цель - горизонтальное масштабирование, когда объем данных и нагрузка не помещаются в один сервер.
    3. Данные делятся по определенному ключу (например, географическому региону, ID пользователя), что позволяет параллельно обрабатывать запросы на разных шардах.
    4. Требует сложной логики маршрутизации запросов и управления целостностью между шардами.

## Что такое wal-файл и зачем он нужен?  
- Ответ  
  WAL (Write-Ahead Logging) - механизм журналирования в PostgreSQL который записывает все изменения данных перед тем, как они попадут на диск.       
  По сути это страховка для базы данных, помогающая не потерять данные, если что-то пойдет не так.    

  Задачи:    
  1. Обеспечение целостности и надежности данных  
    * В случае сбоя системы или краха данных  
    * При внезапном отключении питания  
    * При аппаратных проблемах  
  
  2. Репликация  
    * Wal используется для синхронизации реплик  
    * Обеспечивает последовательное применение изменений  

  3. Оптимизация производительности  
    * Изменения сначала записываются в wal файл (быстрая последовательная запись)  
    * После чего происходит асинхронное обновление основных файлов базы (медленные случайные операции I/O)  
  
  4. Point-in-time-recovery   
    * Позволяет восстановить базу данных на любой момент времени  
    * Помогает при случайном удалении или повреждении данных  
    * Позволяет откатиться к определенной точке

## Как безопасно удалить или изменить миллион строк в базе данных?  
- Ответ  
  
  Если просто в лоб удалять таблицу через DELETE, то мы можем столкнуться с блокировками таблицы. То есть таблица какое-то время будет недоступна.   
  Также можно столкнуться с повышенной нагрузкой на систему, что также замедлит общую производительность запросов.  
  1. Создать временную таблицу, с той же структурой, что и у текущей таблицы. Скопировать туда нужные данные. Потом переименовать таблицы. И удалить старую ненужную. В некоторых случаях это быстрее.  
  2. Порционное удаление. То есть мы разбиваем удаление по частям, например по 1000 записей. Можно оставить задержку между удалением. (Нужно это делать в транзакции).  
  3. Нужно найти время, когда нагрузка на базу минимальная. Как правило, это ночное время.  
  4. На всякий случай создать резервную копию базы.

## Что такое Kafka и зачем оно нужно

- Ответ

    Apache Kafka - это распределённая платформа обмена сообщениями в режиме реального времени, которая обеспечивает высокую пропускную способность и надёжность передачи данных между различными системами и приложениями. Она работает как брокер сообщений, позволяя приложениям-продюсерам отправлять сообщения в так называемые топики, а приложениям-консьюмерам (потребителям) получать эти сообщения подпиской на нужные топики.​

    Основные характеристики Kafka:
    1. Сообщения записываются в лог (топик), который разбивается на партиции для параллелизма и масштабируемости.
    2. Каждое сообщение получает уникальный offset, что позволяет потребителям читать данные с нужной позиции.
    3. Партиции реплицируются между брокерами для отказоустойчивости.
    4. Поддерживает высокую пропускную способность и низкую задержку.
    5. Используется для интеграции микросервисов, потоковой обработки данных, событийных систем и систем сбора логов

- Опишите архитектуру типового решения с Kafka: продюсеры, брокеры, консюмеры, потоковая обработка

    Продюсеры (Producers):
    1. Это приложения или сервисы, генерирующие и отправляющие сообщения в Kafka.
    2. Продюсер пишет данные в определённый топик.
    3. Сообщения автоматически распределяются между партициями топика для масштабируемости.

    Брокеры (Brokers):
    1. Серверы, которые формируют кластер Kafka.
    2. Каждый брокер хранит части топиков - партиции.
    3. Брокеры реплицируют данные для отказоустойчивости, и в случае сбоя одного брокера другие продолжают работу.

    Топики и партиции (Topics & Partitions):
    1. Топик - логический канал для сообщений.
    2. Топик делится на партиции, каждая из которых упорядочена и имеет уникальные смещения (offset).
    3. Партиционирование позволяет размещать разные части топика на разных брокерах, обеспечивая горизонтальную масштабируемость и параллельную обработку.

    Консьюмеры (Consumers) и группы консьюмеров (Consumer Groups):
    1. Консьюмеры читают сообщения из топиков.
    2. Группа консьюмеров объединяет несколько консьюмеров, которые совместно читают данные, распределяя партиции между собой.
    3. Это обеспечивает масштабируемость и балансировку нагрузки при потреблении данных.

    Потоковая обработка (Stream Processing):
    1. Kafka интегрируется с системами потоковой обработки (например, Kafka Streams, Apache Flink), которые позволяют обрабатывать данные в реальном времени, выполнять преобразования, агрегации и фильтрацию.
    2. Потоковая обработка обеспечивает построение сложных бизнес-логик и аналитики на лету

## Какие параметры конфигурации важны при настройке кластера Kafka?

- Ответ

    1. num.partitions - количество партиций по умолчанию для создаваемых топиков; влияет на параллелизм и масштабируемость.
    2. default.replication.factor - коэффициент репликации партиций, определяет количество копий данных для отказоустойчивости.
    3. min.insync.replicas - минимальное число реплик, которые должны подтвердить запись для успешного коммита, влияет на баланс между консистентностью и доступностью.
    4. log.dirs - директории для хранения логов брокера, важно для распределения нагрузки и производительности.
    5. message.max.bytes - максимальный размер сообщения, помогает контролировать нагрузку и размер сетевых пакетов.
    6. num.io.threads и num.network.threads - число потоков для ввода-вывода и сетевых операций, влияют на пропускную способность брокера.
    7. auto.create.topics.enable - разрешает или запрещает автоматическое создание топиков, что важно для контроля схемы данных.
    8. unclean.leader.election.enable - настройка для разрешения выборов лидера с неполными репликами, которая влияет на доступность и целостность данных.
    9. log.retention.hours и log.retention.bytes - параметры управления временем хранения и размером логов, важные для очистки старых данных.
    10. zookeeper.connect или KRaft mode - параметры для управления метаданными кластера через ZooKeeper или встроенный контроллер с KRaf

## Как мониторите Kafka: какие метрики, алерты, дашборды используете?

- Ответ

    Метрики для мониторинга:
    1. Lag консьюмера (Consumer Lag): Отставание консьюмера от лидера партиции, критично для оценки актуальности потребляемых данных.
    2. Under-replicated Partitions: Количество партиций с неполным набором реплик, указывает на проблемы с репликацией.
    3. Offline Partitions: Партиции, которые временно недоступны - важный показатель отказов.
    4. Produce/Fetch Request Rate & Latency: Частота и задержка запросов на запись и чтение сообщений, отражает производительность брокеров.
    5. ISR (In-Sync Replicas) size: Количество реплик, которые синхронизируются с лидером, показывает стабильность репликации.
    6. Брокер CPU, память, дисковая подсистема: Ресурсы сервера, которые влияют на производительность кластера.
    7. Состояние ZooKeeper или KRaft: Здоровье координационного сервиса.
