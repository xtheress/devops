## Чем отличается виртуализация и контейнерезация?

- Ответ
    
    Виртуализация и контейнеризация — это технологии, позволяющие создавать изолированные среды для приложений, но они различаются по архитектуре и уровню изоляции.

    Виртуализация
    1. Создаёт виртуальные машины (ВМ), которые полностью эмулируют аппаратное обеспечение, включая процессоры, память, устройства ввода-вывода и собственную операционную систему.
    2. Каждая ВМ работает независимо, имеет своё ядро ОС и полную изоляцию от других ВМ и хоста.
    3. Требует больше ресурсов, так как каждой ВМ нужно загружать полноценную ОС.
    4. Управляется гипервизором, который выделяет ресурсы ВМ и обеспечивает безопасность.
    5. Запуск и остановка ВМ занимает больше времени из-за загрузки ОС.
    6. Подходит для запуска окружений с разными операционными системами и высоким уровнем изоляции.

    Контейнеризация
    1. Создаёт контейнеры, которые изолируют приложение и его зависимости, используя общее ядро операционной системы хоста.
    2. Контейнеры легче и потребляют меньше ресурсов, так как внутри нет отдельной ОС — только приложение со всеми нужными библиотеками.
    3. Запуск контейнера крайне быстрый, они легко масштабируются и портируемы между средами (разработка, тест, прод).
    4. Изоляция слабее, чем у ВМ, так как все контейнеры используют одно ядро ОС, что создаёт определённые риски при уязвимостях ядра.
    5. Управление контейнерами упрощено с помощью платформ типа Docker, Kubernetes.
    6. Подходит для микросервисной архитектуры и сценариев быстрого развертывания.

## Что такое docker и какие инструменты linux лежат в основе? Для чего он используется?

- Ответ
    
    Docker базируется на технологиях **namespaces**, **cgroups**, **capabilities**, **overlay**
    **namespaces** - обеспечивает изоляцию. Используется для изоляции. Например, можно айдишники процессов разместить в разных контейнерах.
    **cgroup** - штука, которая позволяет управлять группой процессов, и управлять их ресурсами.
    **capabilites** - штука, которая позволяет дать некоторые рут привелегии процессам или исполняемым файлам. Например, изменить UID процесса на 0, или дать возможность монтировать файловые системы.
    **overlay (overlayFS, overlay2-драйвер)** - файловая система, которая умеет работать "слоями". Не сохранять каждый раз новые файлы, а наслаивать один слой на другой, тем самым экономя место на диске и время создания контейнера. 
    
    А вот докер - это уже штука, которая всеми этими технологиями рулит. Да ещё и удобным для нас образом.
    
    Компоненты докера:  
    1. Docker Daemon — это серверная часть, она работает на хост-машине: скачивает образы и запускает из них контейнеры, создаёт сеть между контейнерами, собирает логи. Когда мы говорим «создай образ», этим тоже занимается демон
    2. Docker CLI — клиентская часть Docker, консольная утилита для работы с демоном. Повторю, она может работать не только локально, но и по сети
    3. Dockerfile — инструкция по тому, как собирать образ.
    4. Docker Image — образ, из которого раскатывается контейнер.
    5. Docker Container - запущенный образ приложения, который кроме нижних слоев в режиме "только чтение" содержит верхний слой в режиме "чтение-запись"
    6. Docker registry — хранилище образов.


- Что такое Docker(image) образ?
    
    **Образ** - шаблон приложения, который содержит слои файловой системы в режиме "только-чтение". Создаются из Dockerfile

    Образ - Это неизменяемый образ, из которого разворачивается контейнер. Его можно рассматривать как набор файлов, необходимых для запуска и работы приложения на другом хосте. Можно привести аналогию из мира установки ПО: образ — это компакт-диск, с которого устанавливается программа

    Dockerfile состоит из различных инструкций:
    1. FROM — задаёт базовый образ, от которого строится новый образ. Обязательная первая инструкция.
    2. RUN — выполняет команду в контейнере во время сборки образа, например, установку пакетов.
    3. LABEL — добавляет метаданные к образу в виде пар ключ-значение.
    4. EXPOSE — объявляет порт(ы), которые контейнер слушает во время выполнения.
    5. ARG - объявляет аргументы сборки, доступные только в процессе сборки
    6. ENV — задаёт переменные окружения внутри контейнера, которые доступны и после сборки
    7. ADD — копирует файлы, каталоги или архивы с хоста в контейнер, может распаковывать архивы и загружать файлы по URL.
    8. COPY — копирует файлы и директории с хоста в контейнер.
    9. VOLUME — объявляет точки подключения томов для хранения данных вне контейнера.
    10. ENTRYPOINT — задаёт основной исполняемый файл контейнера, команда CMD добавляется как аргументы, не переопределяется.
    11. CMD — задаёт команду по умолчанию при запуске контейнера (может быть переопределена).
    12. USER — указывает пользователя для выполнения команд внутри контейнера

    Порождают слои:
    FROM
    RUN
    COPY
    ADD
    LABEL
    ENV

## Какие есть best practices для написания Dockerfile?

- Ответ
    1. Запускать только один процесс на контейнер.
    2. Стараться объединять несколько команд **RUN** в одну для уменьшения количества слоёв образа.
    3. Частоизменяемые слои образа необходимо располагать ниже по уровню,
    чтобы ускорить процесс сборки, т.к. при изменении верхнего слоя, все
    нижеследующие слои будут пересобираться.
    4. Указывать явные версии образов в инструкции **FROM**, чтобы избежать случая, когда выйдет новая версия образа с тегом **latest**.
    5. При установке пакетов указывать версии пакетов.
    6. Очищать кеш пакетного менеджера и удалять ненужные файлы после выполненной инструкции.
    7. Использовать **multistage build** для сборки артефакта в одном контейнере и размещении его в другом.

## Команды Docker
  Управление контейнерами:
  1. docker run <образ> — создать и запустить новый контейнер из образа.
  2. docker start <контейнер> — запустить уже созданный контейнер.
  3. docker stop <контейнер> — остановить работающий контейнер.
  4. docker restart <контейнер> — перезапустить контейнер.
  5. docker kill <контейнер> — отправить сигнал SIGKILL для принудительной остановки.
  6. docker rm <контейнер> — удалить остановленный контейнер.
  7. docker ps — вывести список работающих контейнеров.
  8. docker ps -a — показать все контейнеры, включая остановленные.
  9. docker exec -it <контейнер> <команда> — выполнить команду внутри запущенного контейнера (например, открыть shell).

  Управление образами:
  1. docker build -t <имя_образа> . — собрать образ из Dockerfile.
  2. docker pull <образ> — загрузить образ из репозитория (Docker Hub).
  3. docker push <образ> — отправить локальный образ в репозиторий.
  4. docker images — показать список локальных образов.
  5. docker rmi <образ> — удалить образ.

  Управление томами (Volumes):
  1. docker volume create <имя> — создать том.
  2. docker volume ls — список томов.
  3. docker volume rm <имя> — удалить том.

  Управление сетями:
  1. docker network create <имя> — создать сеть.
  2. docker network ls — показать сети.
  3. docker network rm <имя> — удалить сеть.

  Работа с логами и информацией:
  1. docker logs <контейнер> — вывести логи контейнера.
  2. docker inspect <контейнер/образ> — получить подробную JSON-информацию.
  3. docker stats — мониторинг ресурсов контейнеров.

  Другие полезные команды:
  1. docker cp <src> <container>:<dest> — копировать файлы между хостом и контейнером.
  2. docker-compose -f up

## Какие типы сетей есть в докере

- Ответ  
  **bridge** - Это стандартная сеть по умолчанию, которая создает виртуальный мост (bridge) для обмена данными между контейнерами. Каждый контейнер получает собственный IP-адрес из диапазона сети Docker.

  **host** - использует сетевой стек хоста, что означает, что контейнеры не изолированы на уровне сети от хоста. То есть, контейнер не изолирован по портам и делает запросы напрямую через сеть хоста.

  **none** - контейнер не имеет доступа к сети.

  **overlays** - тип сетей которые пересекают несколько узлов. Полезно когда у тебя docker контейнеры запушенны на разных хостах, но они должны общаться между собой. Для реализации этой сети Docker использует технологии, такие как **VXLAN** (Virtual Extensible LAN).


- Настроить сетевое взаимодействие между двумя docker-контейнерами
        
    - Контейнеры должны быть частью одной сети
    - Докер создает виртуальную сеть, default bridge и подключает к ней контейнеры. Также, использует драйвер overlay для многохостовых сетей
    - В сети контейнерам назначается айпишник
    - Если контейнеры имеют выход в большую сеть, то они ведут себя как программы на отдельных компах

    Пример с сетевым драйвером bridge:
    1. Создаем сеть
       ```
       docker network create my_network
       ```
    2. Запускаем два контейнера в сети (sleep 1d это для бездействия контейнера в течение дня. Полезно при дебаге порой):
       ```
        docker run -d --name container1 --network my_network alpine sleep 1d
        docker run -d --name container2 --network my_network alpine sleep 1d
       ```
    3. Пробуем попинговать по имени:
       ```
        docker exec -it container1 ping container2
        ubuntu@host:~$ docker exec -it container1 ping container2

## От кого по умолчанию запускается контейнер? Почему это плохо?

- Ответ

    Процесс внутри пользователя запускается от root.
    Плохо:
    1. Высокие привилегии: Запуск от root увеличивает риск безопасности, так как в случае уязвимости внутри приложения или контейнера злоумышленник может получить полный контроль внутри контейнера.
    2. Эскалация прав: Если хост настроен ненадлежащим образом, атака может перейти с контейнера на хост-систему.
    3. Доступ к файловой системе: Root-пользователь имеет полный доступ ко всем файлам и процессам в контейнере, что увеличивает потенциальный ущерб.
    4.  Нарушение принципа наименьших привилегий: По безопасности рекомендуется запускать процессы с минимально необходимыми правами для уменьшения векторов атаки

    Пакеты можно поставить от рута, а потом применить директиву USER

## Возможен ли самостоятельный перезапуск контейнера?

- Ответ
    
    Да, можно вот так указать:
    
    `docker run --restart=always`
