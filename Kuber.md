## Что такое kubernetes?

- Ответ

    Kubernetes - это платформа с открытым исходным кодом для управления контейнерами, которая автоматизирует развертывание, масштабирование и эксплуатацию контейнеризированных приложений и сервисов. Она позволяет запускать, контролировать и балансировать контейнеры на кластере серверов, обеспечивая высокую доступность, отказоустойчивость и эффективное использование ресурсов.​

    Основные задачи Kubernetes:
    1. Оркестрация: автоматизация управления жизненным циклом контейнеров (создание, удаление, обновление, масштабирование).​
    2. Балансировка нагрузки: распределение трафика между экземплярами приложений.​
    3. Автоматизация обновлений и откатов: безопасное внедрение изменений в приложениях.​
    4. Управление хранением данных: монтаж и управление внешними хранилищами для контейнеров.​
    5. Мониторинг сервисов и восстановление после сбоев: автоматический перезапуск контейнеров при сбоях, масштабирование в зависимости от нагрузки

## Опиши архитектуру кубернетес кластера, из чего состоит?

- Ответ

    Kubernetes кластер состоит из двух основных компонентов: Master nodes(Control plane) и Worker nodes

    **Master nodes/Control plane**:
    Это «мозг» кластера, отвечающий за принятие решений и управление состоянием приложения

    Минимальное кол-во нод 3:
    1. При одной ноде отказ бы означал полное прекращение работы кластера.
    2. Две ноды создают риск "разделения мозга" (split-brain), когда каждая нода может считать себя ведущей, что приводит к нестабильности.
    3. Три ноды позволяют организовать кворум (большинство) для управляющих компонентов и распределённых хранилищ (например, etcd), обеспечивая надёжность и согласованность данных.
    4. С тремя и более нодами кластер автоматически перенесёт нагрузку с отказавшей ноды на остальные.

    Из чего состоит Control plane:
    1. kube-apiserver - центральная точка взаимодействия с кластером, обрабатывает REST-запросы от пользователей и компонентов, валидирует и записывает состояние в хранилище.
    2. etcd - распределённое высокодоступное хранилище ключ-значение, которое хранит все данные о состоянии кластера.
    3. kube-scheduler - планировщик, который решает, на какой рабочий узел назначить поды, основываясь на доступных ресурсах.
    4. kube-controller-manager - управляет контроллерами, которые следят за состоянием кластера (например, за нужным числом реплик подов, состоянием узлов).
    5. cloud-controller-manager (опционально) - интеграция с облачными провайдерами для управления ресурсами.


    **Воркер-нода**:
    Это «мышцы» кластера, которые запускают контейнеры и выполняют приложения:
    1. kubelet - агент, работающий на каждой ноде, который получает команды из управляющего слоя, запускает и контролирует поды.
    2. kube-proxy - обеспечивает сетевую маршрутизацию и балансировку нагрузки между подами на разных узлах.
    3. Container Runtime - система запуска контейнеров (например, containerd, CRI-O, Docker).

- Объекты кластера кубернетес
    Pods:
    1. Минимальная единица развертывания в Kubernetes.
    2. Содержит один или несколько контейнеров, совместно использующих сеть и хранилище.
    3. Поддерживает жизненный цикл приложений.
    Для них существуют Volume (это абстракция файлового хранилища):
    - Volume обеспечивает сохранение данных вне жизненного цикла контейнера
    - Совместное использование данных между несколькими контейнерами одного пода.
    - Подключение внешних и локальных хранилищ
    Виды Volume:
    emptyDir - временный том, создаётся при запуске пода и исчезает при удалении пода.
    hostPath - подключение локальной директории с ноды

    Persistent Volumes (Постоянные тома, можно отнести к ресурсам кластера):
    1. Абстракция хранения, независимого от жизненного цикла подов.
    2. Обеспечивают сохранность данных.
    PersistentVolumeClaim (PVC) - запрос на использование PV и ресурс хранения для пода.



    Nodes (Ноды):
    1. Физические или виртуальные машины, на которых запускаются поды.
    2. Делятся на мастер-ноды (управляют кластером) и воркер-ноды (запускают приложения).


    Services (Сервисы):
    1. Определяют стабильный сетевой доступ к подам.
    2. Позволяют организовать балансировку нагрузки и обнаружение сервисов.
    Типы Services:
    - ClusterIP - по умолчанию. Сервису выделяется отдельный айпишник внутри кластера. Доступ возможен только внутри кластера.
    - NodePort - открывает фиксированный порт на каждой ноде, возможен доступ снаружи кластера
    - LoadBalancer - Предоставляет внешний IP-адрес для доступа к приложению, интегрируется с внешними балансировщиками нагрузки
    - ExternalName - Создаёт внутри кластера DNS-имя, которое ссылается на внешний ресурс. Позволяет обращаться к внешним сервисам по удобному имени
    - Headless Service - Сервис без выделенного ClusterIP. Используется для прямого доступа к подам, например, в распределённых базах данных. Обеспечивает DNS-записи для каждого пода


    Deployments (Развертывания)
    1. Управляют жизненным циклом подов и реплик.
    2. Автоматически создают, обновляют и масштабируют поды.


    ReplicaSets (Наборы реплик)
    1. Обеспечивают запрошенное количество реплик пода, поддерживая их количество в кластере.


    StatefulSets, DaemonSets, Jobs, CronJobs:
    1. StatefulSets - это контроллер для управления приложениями, которые требуют сохранения состояния, таких как базы данных, очереди сообщений и другие
    2. DaemonSets - запускают поды на каждой ноде (одна копия), запускает сборщики логов и развертывает мониторинговые сервисы.
    3. Jobs - однократное выполнение задач.
    4. CronJobs - выполнение по расписанию.


    Namespaces (Пространства имен):
    1. Логическое разделение ресурсов внутри одного кластера.
    2. Позволяют изолировать приложения и управлять ресурсами.

## Что такое configMap?

- Ответ
    
    Это объект, который используется для хранение неконфиценциальных параметров типа ключ-значение.
    - Хранение настроек, параметров, URL, конфигурационных файлов и других данных, необходимых приложению.
    - Возможность передавать данные в контейнер как переменные окружения, аргументы командной строки или файлы, монтируемые в под.
    - Отделение конфигурации от контейнерного образа, что упрощает обновление параметров без пересборки образа.
    - Поддержка управления конфигурацией для разных окружений (разработка, тестирование, продакшн)

## Что такое Readiness, Liveness, Startup пробы, какое отличие?

- Ответ

    Для чего нужны пробы. Дело в том, что запущенный под это не значит запущенное и развернутое приложение. Какая-нибудь джава может по пять минут подниматься.  
    Соответственно, нам нужно убедиться в том, что приложение запущено, и что на под можно пускать трафик

    **Startup** пробы, чтобы понять, когда приложение в контейнере было запущено. Если проба настроена, он блокирует Liveness и Readiness проверки, до того как проба становится успешной
    
    **Liveness** пробу для проверки, когда перезапустить контейнер. Например, Liveness проба должна поймать блокировку, когда приложение запущено, но не может ничего сделать. В этом случае перезапуск приложения может помочь сделать приложение доступным, несмотря на баги.
    
    **Readiness** пробы, чтобы узнать, готов ли контейнер принимать траффик. Pod считается готовым, когда все его контейнеры готовы.

## Что такое Ingress

- Ответ

    Это объект, который управляет внешним доступом к сервисам в кластере, обычно через HTTP или HTTPS. Он предоставляет правила маршрутизации входящего трафика, определяя, как запросы с внешних адресов должны направляться к конкретным сервисам внутри кластера.

    Работает вместе с Ingress Controller - компонентом, который реализует правила, заданные в Ingress, и обрабатывает внешний трафик (например, NGINX, Traefik).

## Что такое Requests, Limits?

- Ответ

    Requests и Limits в Kubernetes - это настройки управления ресурсами (CPU, память) для контейнеров и подов, которые определяют минимальные и максимальные ресурсы, выделяемые для их работы.

    Requests (запросы):
    1. Определяют минимальное количество ресурсов, которое Kubernetes гарантирует выделить поду или контейнеру.
    2. Планировщик Kubernetes учитывает requests при назначении пода на узел, не размещая под, если на узле недостаточно ресурсов.
    3. Помогают гарантировать стабильную работу, обеспечивая под необходимыми ресурсами.

    Limits (лимиты):
    1. Задают верхний предел ресурсов, которые контейнер может использовать.
    2. Если контейнер пытается превысить лимит CPU, его работа может быть ограничена (throttling).
    3. Если контейнер превышает лимит памяти, он может быть принудительно перезапущен (OOMKilled).
    Limits предотвращают чрезмерное потребление ресурсов одним контейнером, защищая остальные приложения.

## Affinity, anti-affinity**

- Ответ

    Affinity и Anti-affinity в Kubernetes - это механизмы, позволяющие управлять тем, как поды размещаются относительно узлов (nodes) и других подов для оптимального распределения и повышения отказоустойчивости.

    Affinity:
    1. Node affinity - привязка пода к узлам с определёнными метками. Позволяет запланировать под на узлы с нужными характеристиками (например, с GPU, SSD).
    2. Pod affinity - указывает, что поды желательно размещать близко друг к другу (например, на одном узле или в одной зоне) для сокращения задержек и повышения производительности.
    3. Node affinity и pod affinity бывают строгими (required) и предпочтительными (preferred).

    Anti-affinity:
    1. Правила anti-affinity обеспечивают, чтобы поды не запускались вместе, то есть избегают размещения определённых подов на одном узле или близко по топологии.
    2. Часто применяется для равномерного распределения реплик приложений по узлам или зонам, снижая риск одновременного сбоя.
    3. Также бывают строгие и предпочтительные правила.

## Что такое Taints, Tolerations?

- Ответ

    Taints и Tolerations в Kubernetes - два взаимосвязанных механизма, позволяющих гибко управлять размещением подов на узлах кластера.

    Что такое taints:
    1. Taints ("тейнты") - специальные политики или метки, которые назначаются узлам (nodes).
    2. Узел с taint будет "отталкивать" поды - то есть не позволит им запускаться, если только у пода нет соответствующего toleration.
    3. Позволяют изолировать определённые узлы, например, для специализированной нагрузки (узлы с GPU, важные сервисы и т.д.).

    Что такое tolerations:
    1. Tolerations ("толерансы") - разрешения для подов запускаться на узлах с определёнными taints.
    2. Задаются в манифесте пода и позволяют ему "терпеть" соответствующие ограничения от taint и быть запущенным на таком узле, несмотря на taint.
    3. Применяются только к подам, никак не влияют на сами узлы

## Что такое Helm

- Ответ
    
    Пакетный менеджер для кубера.
    Шаблонизатор для управления.
    Позволяет упаковывать Kubernetes ресурсы приложения в единые пакеты - чарты (Helm Charts)
    
    Пакет в helm это набор yml и tpl файлов.
    Также может использовать jinja2 template в качестве шаблонизатора

    Helm даем:
    1. Версионирования.
    2. Шаблонизирование.
    3. Удобство развертывания инфраструктуры на разные контура.
    4. Более подконтрольная работа с конкретной разворачиваемой инфраструктурой.
    5. Возможность подтягивать зависимости. Допустим  если у тебя хелм чарт 
       зависит от другого хелм чарта, ты можешьб либо в самом Chart.yml 
       файле в директиве dependency прописать зависимотси, либо 
       в отдельном файле requirements.yml прописать все зависимости
       и перед раскаткой основного хелм чарта поднятнуть все зависимости командой 
       `helm dependency update`.

## Что такое Secret

- **Ответ**
    
    Объект, который содержит конфиденциально важное значение. (пароль, токен, ключ).
    
    Хранение важных параметров в виде секретов более безопасно и гибко, чем включение их в конфигурацию пода или в образы контейнеров.
    
    Для использования секрета поду необходимо указать его.
    
    Секрет может использоваться следующими способами:
    - Файл подключенный через volume контейнера.
    - Значение переменной окружения
    - kubelet использует секреты для подключения к апи серверу, для загрзки образов из докер регистри

    Минусы хранения секретов в kube:
    - данные не шифруются, а толкьо кодируются в base64, данные можно декодировать обратно
    - любой кто имеет доступы на чтения секретов в кубе может их получить
